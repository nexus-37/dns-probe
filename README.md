# DNS в России: измерительный скрипт

Скрипт к исследованию **«Что происходит с DNS в России? Ищем признаки цензуры»** — [te-st.org, 7 августа 2026](https://te-st.org/2026/08/07/dnsdnsdns/), Теплица социальных технологий.

Если вы здесь после того, как прочитали статью и хотите проверить методологию сами — это то место. Если вы здесь случайно — сначала прочитайте саму статью, без неё скрипт мало что объяснит.

## Что делает скрипт и почему он устроен именно так

`dns_probe_v4.sh` опрашивает список DNS-резолверов (Google, Cloudflare, Quad9, AdGuard, Яндекс и другие — полный список см. в самом скрипте) по списку доменов (заблокированные мессенджеры, СМИ, контрольные домены и т.д.) через четыре транспорта: обычный DNS (UDP/53), DNS-over-TLS, DNS-over-HTTPS и DNS-over-QUIC.

Несколько решений в архитектуре скрипта не случайны — вот зачем они нужны:

- **Проходы по кругу, а не подряд по одному домену.** Скрипт делает несколько полных проходов по всем доменам (по умолчанию 5), а не спрашивает один домен пять раз подряд, потом следующий. Так DNS-трафик меньше похож на автоматизированный бот-паттерн для тех, кто может его анализировать на пути.
- **Захват TTL и задержки на каждый запрос.** Это не только сам IP-ответ, но и вспомогательные метрики, которые потом помогают отличить честную anycast-балансировку нагрузки от подмены ответа.
- **Поддержка DoQ проверяется отдельно для каждого резолвера**, а не один раз глобально — если конкретный резолвер не поддерживает DoQ, это фиксируется именно для него, а не выключает протокол для всех остальных разом.
- **Внутренний идентификатор резолвера** (CHAOS TXT `id.server`/`hostname.bind`), если резолвер готов его отдать — полезно, чтобы понимать, отвечает ли один и тот же физический сервер на разных прогонах.

Каждый запуск скрипта на одной точке измерения даёт один JSON-файл с результатами этого прогона.

## Как запустить

Нужны: `bash`, `jq`, `kdig` (пакет `knot-dnsutils`), `curl`, `bc`. Скрипт сам попробует их доставить через `apt-get`, если каких-то нет.

```bash
chmod +x dns_probe_v4.sh
./dns_probe_v4.sh
```

Настройки через переменные окружения:

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `REPEATS` | 5 | сколько полных проходов по всем доменам |
| `BASE_DELAY` | 1 | базовая пауза между запросами (сек) |
| `JITTER_MAX` | 2 | плюс случайная добавка 0…N сек к паузе |
| `EXTERNAL_IP_CHECK_EVERY` | 10 | как часто дополнительно сверять внешний IP через ipinfo.io (раз в N доменов) |
| `BASELINE_FILE` | — | см. раздел «Сравнение с эталоном» ниже |
| `KDIG_TIMEOUT` | 3 | таймаут отдельного DNS-запроса (сек) |

Пример: более быстрый прогон с 2 повторами вместо 5:
```bash
REPEATS=2 ./dns_probe_v4.sh
```

## Killswitch: зачем скрипт сам себя останавливает

Скрипт написан с расчётом, что его будут запускать не только мы — в будущем, возможно, и другие люди на своих точках подключения. А в реальных условиях с сетью в процессе долгого прогона (он может идти час и больше) может случиться что угодно: кто-то по привычке включит или выключит VPN прямо во время теста; отвалится домашний Wi-Fi и роутер молча переключится на резервный мобильный интернет; провайдер перекинет соединение на другой канал.

Если это произойдёт незаметно, результат окажется кашей — часть запросов внутри одного файла пойдёт с одной сети, часть с другой, и разобраться, где что, будет уже невозможно постфактум. Поэтому скрипт на каждой итерации дёшево проверяет, не поменялся ли исходящий адрес (`ip route get`), а заодно раз в `EXTERNAL_IP_CHECK_EVERY` доменов дополнительно сверяет внешний IP через ipinfo.io. Если что-то изменилось — скрипт сразу останавливается (`exit 1`), а не продолжает писать в файл данные вперемешку.

## Сравнение с эталоном (`BASELINE_FILE`)

Идея, которая пока не реализована на практике в этом цикле измерений, но заложена в код: сделать один прогон на заведомо «чистом» подключении без цензуры, передать этот JSON скрипту через `BASELINE_FILE`, и тогда каждый новый прогон (например, с исследуемого узла в России) будет сразу помечать в поле `baseline_mismatch`, отличается ли ответ от эталонного. В опубликованном исследовании эта функция в коде есть, но реальным эталонным файлом мы не пользовались — сравнение между узлами делали вручную после сбора всех данных.

## Что означают поля в JSON-выводе

```jsonc
{
  "timestamp": "...",       // время старта прогона (UTC)
  "node_ip": "...",         // внешний IP точки измерения на момент старта
  "city": "...",            // геолокация по данным ipinfo.io
  "repeats": 5,
  "dns_resolution_tests": [
    {
      "pass": 1,                     // номер прохода
      "group": "Messengers",         // категория домена
      "domain": "signal.org",
      "resolver": "Google",
      "node_id": "...",              // ответ CHAOS TXT резолвера, если есть
      "udp_53":   {"answer": "...", "ttl": 0, "latency_ms": 0},
      "dot_853":  {"answer": "...", "ttl": 0, "latency_ms": 0},
      "doh_443":  {"answer": "...", "ttl": 0, "latency_ms": 0},
      "doq_853":  {"answer": "...", "ttl": 0, "latency_ms": 0},
      "baseline_mismatch": null      // true/false/null — см. «Сравнение с эталоном» выше
    }
  ]
}
```

`answer` может быть либо списком IP-адресов через запятую, либо одним из служебных значений:
- `TIMEOUT_OR_ERROR` — не дождались валидного ответа за `KDIG_TIMEOUT`;
- `NOT_SUPPORTED` — у этого резолвера нет соответствующего шифрованного транспорта;
- `NOT_TESTED_LOCAL` — сам бинарник `kdig` на этой машине не умеет DoQ (нужен Knot DNS ≥ 3.2).

## Про данные (CSV и сырые JSON)

Мы сознательно не публикуем ни сырые JSON-файлы (в них открытым текстом есть реальные IP-адреса и геолокация наших измерительных точек), ни агрегированный CSV — это вопрос безопасности людей, которые проводили измерения, а не желание что-то скрыть по существу.

Данные есть в распоряжении редакции. Если у вас есть конкретный обоснованный вопрос по конкретной находке — напишите нам (контакты ниже), и мы разберём этот случай отдельно. Честно говоря, даже анонимизированный CSV без точных адресов и меток времени не даёт стопроцентного доказательства для того, кто в принципе не доверяет исследованию — данные всегда можно назвать сгенерированными. Публикация же добавляет риск для инфраструктуры, но не решает эту проблему. Мы полагаемся на воспроизводимость: любой человек может взять этот скрипт, запустить его сам и получить свою собственную картину. Если она разойдётся с нашей — будем разбирать вместе, что изменилось: ситуация с блокировками в России может поменяться в любой момент, и на момент публикации мы сами не ожидали такого результата.

## Ограничения

- Скрипт не проверяет ODoH, DNSCrypt и децентрализованные системы (OpenNIC и подобные) — это отдельная задача на будущее, см. статью.
- Это рабочий инструмент для одного конкретного цикла измерений, а не готовое к постоянной эксплуатации решение — местами в нём есть упрощения, разумные для разового исследования, но не для непрерывного мониторинга без присмотра.
